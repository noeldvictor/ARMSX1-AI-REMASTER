# Super Enhancement Engine vertical — 2D VRAM-write / framebuffer replacement

## What shipped

A presentation-layer engine in `enhance/` that:

1. Hashes 2D surfaces (CPU-to-VRAM GP0(A0) completions, and the displayed
   framebuffer RGB at present).
2. Auto-applies an algorithmic pass (unsharp + Scale2x) into
   `cache/<serial>/<hash>/{orig,generated}.png`.
3. Composites at present: `user.png` → `generated.png` → original RGB.
4. Exports a pack that copies generated/user and **strips orig.png**.

It never writes `gpu->vram`. Toggle off is the old `qa_frame_rgb` path;
Legaia title hash is unchanged.

## Why the display framebuffer is also hashed

SwanStation's replacement is VRAM-write only. A title screen may be a
textured draw rather than a single LoadImage of the displayed rect. Hashing
the presented RGB as a 2D surface catches the title either way. GP0(A0) is
still observed so individual uploads land in the same cache.

The title's cache key on SCUS-942.54 **is** the unenhanced golden
`1c859cc02ebe806e` — we hash original pixels, then replace. That is the
proof the layer sits above the oracle, not inside it.

## Algorithm

Native RGB → 3×3 unsharp → Scale2x (2× `generated.png`) → box-downsample
back to native for the current QA present size. The 2× file is the pack
asset; native present stays hashable at the original resolution.

Nearest-2× alone is identity at native sampling, which is why unsharp is
in front of Scale2x.

## Not in this vertical

Vulkan present, 3D texture pages, PGXP, file-watcher hot reload, live AI
worker. Algorithmic first pass is enough; AI writes the same
`generated.png` slot later.
