# Letting an AI play the game: the QA harness

## Problem

Every worklog so far has carried the same blocker: *"`bin/armsx` NOT VERIFIED at
runtime."* Autonomous development without a way to observe a running game is
blind. An agent can compile, hash VRAM, and diff source, but it cannot answer
"does the game still boot?" or "did that change break the title screen?"

The FSUI frontend is not a viable answer. It needs a window, a display server,
a human at the keyboard, and its main loop is entangled with 6,500 lines of UI.

## Key insight

**`psx/` has no SDL or frontend dependency, and `psx_run_frame()` advances a
fixed cycle count derived only from emulated state.**

That means a headless driver linking the core alone is possible, and — more
importantly — **deterministic**. Same inputs in, same frames out. Determinism is
what makes a frame hash usable as a regression gate rather than a coin flip.

This is a direct payoff from ADR-001's no-codegen, no-host-threading constraint,
which was originally kept for portability.

## What was built

`tools/armsx_qa.c` (~600 lines) → `build/tools/armsx-qa` via `make qa`.

Links `psx/` plus miniz. **No SDL. No window. No audio device. No host input.**

### Capabilities

| Flag | Purpose |
| --- | --- |
| `--bios=PATH` | BIOS (size-validated at 512 KiB) |
| `--cdrom=PATH` / `--exe=PATH` | disc or PS-X EXE |
| `--frames=N` | run N frames and exit |
| `--script=PATH` | scripted input timeline |
| `--capture-dir=DIR` | write PNG frames |
| `--capture-every=N` / `--hash-every=N` | periodic capture / hashing |
| `--stuck-frames=N` | fail if the image is unchanged for N frames |
| `--json` | one JSON object per event on stdout |
| `--selftest=PATH` | write a test-pattern PNG and exit; no BIOS needed |

### Input script format

Deliberately trivial to generate and to diff:

```
# boot, skip intro, grab the title screen
120  tap     start
240  tap     cross 10      # hold 10 frames
300  press   right
330  release right
360  capture titlescreen
400  hash
600  exit
```

Frames are absolute and need not be ordered — the list is sorted on load.
Unknown commands and unknown button names are hard errors with file:line, not
silent no-ops. A typo in a script must not look like a passing run.

### Machine-readable output

```json
{"event":"start","frames":420,"bios":"...","media":"..."}
{"event":"capture","frame":360,"path":"caps/frame_00000360_titlescreen.png","w":320,"h":240,"hash":"a3f2..."}
{"event":"hash","frame":400,"w":320,"h":240,"hash":"91be..."}
{"event":"done","captures":1,"stuck":false}
```

Exit codes: `0` ok, `2` usage/script error, `3` setup failure, `4` stuck.

## Design decisions

**Standalone tool, not a frontend mode.** Adding headless flags to
`frontend/main.cpp` would mean threading them through an SDL app and a 6,500-line
UI. A separate driver has no SDL dependency at all, builds in seconds, and
cannot destabilise the interactive frontend.

**Stuck detection treats "no display" as a stall.** A frame with no usable
display is a failure signal, not a reason to skip the check. Folding it in as a
sentinel hash means blank-screen hangs are caught. Verified: a zero-filled BIOS
is reported stuck at frame 60 with exit code 4.

**Hash is resolution-sensitive.** Width and height are mixed in deliberately —
a display-mode change is a real difference and should move the hash.

**PNG written by hand.** miniz supplies deflate (its APIs were enabled earlier
this session for the zip test); chunk framing, CRC32 and IHDR are ours. The
`--selftest` flag exists so this path is verifiable without a game, and
`tests/validate_qa.py` checks signature, chunk order, per-chunk CRC, IHDR
fields, zlib validity, decompressed length, and filter bytes.

**A capture an agent cannot open is worse than no capture** — it looks like the
run succeeded. Hence validating the container rather than checking the file is
non-empty.

## Bug found while building this

`psx_cdrom_open()` returns **1 on success and 0 on failure** — inverted from the
usual C convention. The first implementation had the polarity backwards, so a
nonexistent disc path silently "succeeded" and the emulator then spewed illegal
instructions at `bfc00004`, which reads like an emulator bug rather than a bad
argument.

`frontend/main.cpp:1988` gets it right (`== 0` means failure). Noted in
`CLAUDE.md` traps.

## Verified

- `make test-qa` → PNG selftest written and structurally validated.
- Full gate `python3 tests/run_validation.py` → **exit 0, 8 cases** (`web`
  removed with the port deletion, `qa` added).
- PNG independently confirmed with PIL: `256x128 RGB`, `pixel(10,10)=(10,20,0)`
  matching the generator exactly.
- Bad BIOS size → exit 3 with a clear message.
- Nonexistent disc → exit 3 with a clear message.
- Blank output for 60 frames → exit 4, `stuck` reported.
- Malformed script line and unknown button → exit 2 with `file:line`.

## NOT verified

Superseded by [`20260820_1719_qa-functional-boot.md`](20260820_1719_qa-functional-boot.md).
Both local titles now boot; the hashes below this line were the state on
2026-08-20 16:45, before media arrived.

**No real game has been booted.** There is still no BIOS or disc image on this
machine. Everything above was exercised with synthetic inputs — a 512 KiB
zero-filled BIOS and a junk EXE.

The harness is therefore **structurally** verified but not **functionally**
verified against a real title. Boot, input timing, and capture-of-real-content
remain untested.
